## Why Kayan

<CardGrid>
  <Card title="One API in shared code" icon="rocket">
    Kayan generates a typed object in `commonMain`, or in `main` for JVM and Android. Shared code can read config without an Android-only `BuildConfig`.
  </Card>
  <Card title="A fixed merge order" icon="puzzle">
    Base defaults, flavor values, and optional external overrides follow one documented precedence order. A branded build only needs a config file, not a fork of the app.
  </Card>
  <Card title="A schema owned by the app" icon="approve-check-circle">
    The consuming build declares its keys and Kotlin property names. Kayan checks missing values and type mismatches before it generates source. Strict mode rejects unknown keys too.
  </Card>
</CardGrid>

## What you get

<CardGrid>
  <Card title="Use cases" icon="list-format">
    - Gradual migration away from `BuildConfig`
    - White-label products with one shared base config
    - Multi-module builds that share one config file
    - Target-specific KMP values through `expect` / `actual`
    - Compile-time feature flags and endpoints
    - Generated JSON Schema and Markdown docs
  </Card>
  <Card title="Built-in schema types" icon="seti:json">
    - `string`, `boolean`, `int`, `long`, `double`
    - `stringMap`, `stringList`, `stringListMap`
    - `enumValue` for normalized enum generation
    - `custom` adapters for consumer-owned types
  </Card>
</CardGrid>
